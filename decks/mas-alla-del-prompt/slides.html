01

El Prompt

Nick

Primer día en una empresa de IA. Sabe Python, leyó el SDK de OpenAI. Nada más. Y ya tiene un requerimiento sobre la mesa.

El requerimiento

Dado un ticket de soporte, asignarlo al equipo correcto y determinar su prioridad.
Leerlo. Dejarlo respirar. Volvemos a esta frase al final.

Un ticket ambiguo

Llega uno que no encaja. Nick hace lo que haríamos todos: le agrega instrucciones al prompt. Después ejemplos. El prompt empieza a crecer.

El modelo devuelve texto.

Nick necesita una estructura.

A veces la salida ni siquiera se puede parsear. Structured Outputs, JSON Schema, Pydantic. La salida deja de ser una cadena y pasa a ser un objeto validado.

Un solo prompt

  • Clasifica
  • Prioriza
  • Contempla excepciones
  • Aplica reglas de negocio
Todo eso en una sola llamada. Y cada cosa nueva que aparece va al mismo lugar.

Arregla la prioridad.

Rompe la clasificación.

Un prompt que hace todo no se puede tocar. Ahí Nick empieza a versionarlos y escribe sus primeros tests.

Un prompt que decide todo.

Un prompt por decisión.

02

La Orquestación

Caminos distintos

No todos los tickets recorren el mismo camino. Uno de billing no necesita lo mismo que uno técnico.

El código se llena de decisiones

  • Ramas para cada tipo de ticket
  • Reintentos cuando el modelo falla
  • Casos especiales que no encajan
Y llega un punto donde ya nadie sabe por qué camino pasó un ticket.

Deja de ser una función.

Pasa a ser un grafo.

Acá entra LangGraph: StateGraph, nodos, edges condicionales, estado. Está diseñado para workflows stateful con control explícito de la orquestación.

Router

El especialista que corresponda
Billing, technical, sales, priority. Cada uno es un nodo especializado.

Nick mira lo que armó.

Cree que construyó un agente.

03

El Contexto

Un cliente enterprise reporta una caída.

Pausa. Dejarlo instalarse antes de pasar.

Prioridad media.

Nadie se equivocó

  • El prompt estaba bien escrito
  • El grafo ejecutó lo que tenía que ejecutar
  • Nadie sabía del SLA
Este es el giro de la charla. El problema no era el modelo.

Lo que el prompt no sabe

Un prompt no puede inventar lo que no sabe. No importa cuánto lo mejores.

Traerle conocimiento

Ticket
↓
Búsqueda por similitud
↓
Al prompt
Documentación de producto, políticas de soporte, historial de tickets. Acá entra RAG: embeddings y un vector store — pgvector, Pinecone, Qdrant.

Parecido no es correcto

  • Documentos que no vienen al caso
  • Políticas viejas que ya no aplican
  • Y a veces dos que se contradicen

Tenía un problema de prompt.

Ahora tiene uno de recuperación.

Filtrado por metadata, búsqueda híbrida, reranking, reescritura de queries. BM25 combinado con vectores. Rerankers de Cohere o Jina.

Lo que no está en ningún documento

El SLA vigente de ese cliente. Los incidentes abiertos ahora mismo. Eso está en una base de datos y cambia todos los días.

El modelo deja de solo leer.

Ahora también pregunta.

Tool calling: get_customer(), get_sla(), get_active_incidents(). APIs internas, posiblemente vía MCP. Y todo lo que devuelven hay que recordarlo: state con checkpointing.

Las reglas de negocio

Estaban dentro del prompt, mezcladas con las instrucciones. Nick las saca de ahí: config, motor de reglas, o policy-as-code con OPA.

El contexto

ya no se concatena. Se arma.

Retriever, tools, estado, políticas. Dejó de ser un string y pasó a ser un componente con responsabilidad propia.

04

La Evidencia

Sale mal y nadie sabe por qué

  • Qué documentos le llegaron
  • Qué devolvieron las tools
  • Con qué contexto terminó decidiendo
Acá entra tracing. LangSmith, OpenTelemetry, Phoenix. Un trace por ticket: latencia, tokens, costo, ejecución de cada nodo.

Respondió 200.

Y asignó mal el ticket.

Ejecutó bien

Que haya ejecutado bien no significa que haya decidido bien. Y eso ningún trace te lo dice.

Medirlo

  • Los tickets que ya se resolvieron
  • La respuesta correcta ya se conoce
  • Correr el sistema y contar cuántas acierta
Evals. Ground truth de equipo y prioridad. pytest más un harness, o LangSmith / OpenAI Evals. Precision, recall, matriz de confusión.

Antes: que el código no se rompa.

Ahora: que las decisiones no empeoren.

Cambia el prompt, cambia el modelo, cambia el retriever: se corre el dataset otra vez y se compara contra el baseline.

Queda registro

  • Qué evidencia se usó
  • Qué políticas aplicaron
  • Qué modelo decidió, y qué decidió
Traza de decisión persistida. Postgres más los traces de OTel o LangSmith.

No cambió el requerimiento. Cambió lo que Nick entendía del problema.

La complejidad

no la trajo Nick. Siempre estuvo ahí.

La arquitectura no creció por agregar funcionalidades. Creció porque el problema se fue entendiendo. Estaba escondida detrás de un prompt que parecía funcionar.

¿Qué construyó Nick?

  • ¿Un prompt?
  • ¿Un RAG?
  • ¿Un agente?
  • ¿Un grafo?

Todos esos son mecanismos.

Lo estable fue la decisión.

Los mecanismos van a cambiar. Las dos decisiones del día 1 no cambiaron nunca.

Una decisión necesita

  • Contexto para tomarla
  • Evidencia que la respalde
  • Políticas que la limiten
  • Y saber si estuvo bien

Nick no construyó un agente.

Construyó un sistema de decisiones.

El LLM sigue ahí, igual que el día 1.

Construimos todo lo que lo rodea.
