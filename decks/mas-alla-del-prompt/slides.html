Más allá del prompt

Contexto, decisiones y arquitectura para sistemas de IA

Germán Küber

@germankuber

El requerimiento

Dado un ticket de soporte, asignarlo al equipo correcto y determinar su prioridad.
Leerlo entero. Dejarlo respirar. Esta frase no va a cambiar en toda la charla. Guardenla.
Esto es lo que casi todos tenemos en la cabeza cuando decimos “sistema de IA”. Al final de la charla volvemos a este dibujo.

El prompt vive dentro del código.

Cambiar una palabra es un deploy.

Para ajustar una instrucción hay que tocar el repositorio, abrir un PR y esperar el pipeline. Para cambiar una palabra.
El prompt deja de estar hardcodeado. Ahora vive afuera, versionado, y el sistema lo pide antes de cada llamada. Una pieza más. Y todavía no hicimos nada interesante.

El modelo devuelve texto libre.

Alguien tiene que interpretarlo.

A veces viene envuelto en markdown, a veces con una explicación adelante. El parseo se llena de casos especiales.
El sistema ya no habla directo con el modelo: hay un servicio en el medio que arma la consulta, pide el prompt versionado, llama al LLM y procesa lo que vuelve. El LLM devuelve JSON — el servicio lo convierte en una respuesta rica.

Cada llamada elige su propia versión.

Nadie sabe cuál está corriendo.

Un prompt para producción, otro para pruebas, uno viejo que quedó. Hace falta alguien que decida cuál corresponde.
Otra capa. El servicio de consulta ya no habla con el versionador: le pide a un Prompt Service, y ese decide qué versión corresponde. Cada pieza resuelve algo real. Y ninguna hace que el sistema decida mejor.

El cliente era enterprise.

El sistema no tenía cómo saberlo.

Este es el giro. El prompt estaba bien escrito y el sistema ejecutó bien. Pero nadie sabía del SLA. Un prompt no puede inventar lo que no sabe.
Ahora el servicio junta contexto de dos lados antes de llamar al modelo: el prompt versionado y el conocimiento recuperado del RAG. Y esta es la primera pieza que no es plomería — versionar prompts y parsear JSON hacían el sistema mantenible. El RAG le da algo que antes no tenía: información.

Trae documentos parecidos.

No los correctos.

Y encima el SLA de hoy no está en ningún documento: está en una base de datos y cambia todos los días. Nada de eso lo resuelve el retrieval.
Tres piezas más, cada una porque algo falló. El RAG traía documentos parecidos pero no los correctos: aparece el reranking. El SLA de hoy no está en ningún documento: aparecen las tools. Y todo lo que se junta hay que recordarlo: aparece el estado.

Todos los tickets siguen el mismo camino.

No todos lo necesitan.

Uno de facturación no precisa lo mismo que uno técnico. Y las reglas de SLA siguen escondidas adentro del prompt.
Dos piezas más. No todos los tickets recorren el mismo camino: aparece el router, que decide antes de que empiece el trabajo. Y las reglas de SLA, los escalamientos, las restricciones del negocio dejan de vivir dentro del prompt: se vuelven una capa aparte.

Un ticket sale mal.

Nadie puede explicar por qué.

No sabemos qué documentos le llegaron, ni qué devolvieron las tools, ni con qué contexto terminó decidiendo.
Un ticket sale mal y nadie puede explicar por qué: aparece la traza. Guarda qué evidencia se usó, qué políticas aplicaron, qué modelo decidió. Pero ver la ejecución no alcanza — el sistema respondió 200 y decidió mal. Por eso los evals: corren contra tickets ya resueltos y cuentan cuántas acierta.

Nadie puede explicar el sistema entero.

Cada pieza se agregó por una razón buena. Pero ya nadie tiene el mapa completo en la cabeza, y cuando entra alguien nuevo al equipo hay que contarle doce cosas antes de que pueda tocar una. Acá no agregamos nada: ordenamos lo que ya está.
Cuatro capas. Arriba se decide qué hay que decidir. En el medio se arma el contexto para poder decidirlo. Abajo el modelo produce la decisión, y a la derecha queda la evidencia de que estuvo bien. Miren dónde quedó el LLM: una caja más, abajo a la izquierda. Todo lo demás lo construimos nosotros.

Medimos al final.

Y ahí se queda.

Los evals dicen que algo empeoró, y esa información no vuelve a ningún lado.
Es el mismo dibujo. Falta una sola cosa. Sin esa flecha esto es una cascada: medís al final y no pasa nada. Con esa flecha es un sistema que mejora — lo que aprenden los evals vuelve al motor de decisión. Ese ciclo es la diferencia entre medir y mejorar.

Ingeniería
en tiempos de IA

Pausa. Acá cambia el registro: dejamos de mirar el sistema y empezamos a mirar qué significa construirlo.

Lo que cambió

  • Los casos reales son ambiguos
  • Decidir bien necesita saber cosas
  • La evidencia se contradice
  • Sin medirlo, no sabés si funciona
No cambió el requerimiento. Cambió lo que entendíamos del problema.

La complejidad

no la trajimos nosotros. Siempre estuvo ahí.

La arquitectura no creció por agregar funcionalidades. Creció porque el problema se fue entendiendo. Estaba escondida detrás de un prompt que parecía funcionar.

¿Qué construimos?

  • ¿Un prompt?
  • ¿Un RAG?
  • ¿Un agente?
  • ¿Un grafo?

Todos esos son mecanismos.

Lo estable fue la decisión.

Los mecanismos van a cambiar. Las dos decisiones del día 1 no cambiaron nunca.

Una decisión necesita

  • Contexto para tomarla
  • Evidencia que la respalde
  • Políticas que la limiten
  • Y saber si estuvo bien

No construimos un agente.

Construimos un sistema de decisiones.

El LLM sigue ahí, igual que el día 1.

Construimos todo lo que lo rodea.

El prompt no importa

Dejarlo incomodar. Importa, claro que importa — pero no es lo que define si el sistema funciona.

No construimos prompts.
Construimos arquitecturas de IA.
