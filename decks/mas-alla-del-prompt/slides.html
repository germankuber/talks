El requerimiento

Dado un ticket de soporte, asignarlo al equipo correcto y determinar su prioridad.
Leerlo entero. Dejarlo respirar. Esta frase no va a cambiar en toda la charla. Guardenla.
Esto es lo que casi todos tenemos en la cabeza cuando decimos “sistema de IA”. Al final de la charla volvemos a este dibujo.

El prompt vive dentro del código.

Cambiar una palabra es un deploy.

Nick quiere ajustar una instrucción y tiene que tocar el repositorio, abrir un PR y esperar el pipeline. Para cambiar una palabra.
El prompt deja de estar hardcodeado. Ahora vive afuera, versionado, y el sistema lo pide antes de cada llamada. Una pieza más. Y todavía no hicimos nada interesante.

El modelo devuelve texto libre.

Alguien tiene que interpretarlo.

A veces viene envuelto en markdown, a veces con una explicación adelante. El parseo se llena de casos especiales.
El sistema ya no habla directo con el modelo: hay un servicio en el medio que arma la consulta, pide el prompt versionado, llama al LLM y procesa lo que vuelve. El LLM devuelve JSON — el servicio lo convierte en una respuesta rica.

Cada llamada elige su propia versión.

Nadie sabe cuál está corriendo.

Un prompt para producción, otro para pruebas, uno viejo que quedó. Hace falta alguien que decida cuál corresponde.
Otra capa. El servicio de consulta ya no habla con el versionador: le pide a un Prompt Service, y ese decide qué versión corresponde. Cada pieza resuelve algo real. Y ninguna hace que el sistema decida mejor.

El cliente era enterprise.

El sistema no tenía cómo saberlo.

Este es el giro. El prompt estaba bien escrito y el sistema ejecutó bien. Pero nadie sabía del SLA. Un prompt no puede inventar lo que no sabe.
Ahora el servicio junta contexto de dos lados antes de llamar al modelo: el prompt versionado y el conocimiento recuperado del RAG. Y esta es la primera pieza que no es plomería — versionar prompts y parsear JSON hacían el sistema mantenible. El RAG le da algo que antes no tenía: información.

Trae documentos parecidos.

No los correctos.

Y encima el SLA de hoy no está en ningún documento: está en una base de datos y cambia todos los días. Nada de eso lo resuelve el retrieval.
Tres piezas más, cada una porque algo falló. El RAG traía documentos parecidos pero no los correctos: aparece el reranking. El SLA de hoy no está en ningún documento: aparecen las tools. Y todo lo que se junta hay que recordarlo: aparece el estado.

Todos los tickets siguen el mismo camino.

No todos lo necesitan.

Uno de facturación no precisa lo mismo que uno técnico. Y las reglas de SLA siguen escondidas adentro del prompt.
Dos piezas más. No todos los tickets recorren el mismo camino: aparece el router, que decide antes de que empiece el trabajo. Y las reglas de SLA, los escalamientos, las restricciones del negocio dejan de vivir dentro del prompt: se vuelven una capa aparte.

Un ticket sale mal.

Nadie puede explicar por qué.

No sabemos qué documentos le llegaron, ni qué devolvieron las tools, ni con qué contexto terminó decidiendo.
Un ticket sale mal y Nick no puede explicar por qué: aparece la traza. Guarda qué evidencia se usó, qué políticas aplicaron, qué modelo decidió. Pero ver la ejecución no alcanza — el sistema respondió 200 y decidió mal. Por eso los evals: corren contra tickets ya resueltos y cuentan cuántas acierta.

Ya son doce piezas.

Y el dibujo dejó de entrar en una línea.

Momento de parar y reordenar. No agregamos nada nuevo acá: es lo mismo, puesto en capas.
Cuatro capas. Arriba se decide qué hay que decidir. En el medio se arma el contexto para poder decidirlo. Abajo el modelo produce la decisión, y a la derecha queda la evidencia de que estuvo bien. Miren dónde quedó el LLM: una caja más, abajo a la izquierda. Todo lo demás lo construimos nosotros.

Medimos al final.

Y ahí se queda.

Los evals dicen que algo empeoró, y esa información no vuelve a ningún lado.
Es el mismo dibujo. Falta una sola cosa. Sin esa flecha esto es una cascada: medís al final y no pasa nada. Con esa flecha es un sistema que mejora — lo que aprenden los evals vuelve al motor de decisión. Ese ciclo es la diferencia entre medir y mejorar.

El SLA vigente de ese cliente. Los incidentes abiertos ahora mismo. Eso está en una base de datos y cambia todos los días.

El modelo deja de solo leer.

Ahora también pregunta.

Tool calling: get_customer(), get_sla(), get_active_incidents(). APIs internas, posiblemente vía MCP. Y todo lo que devuelven hay que recordarlo: state con checkpointing.

Las reglas de negocio

Estaban dentro del prompt, mezcladas con las instrucciones. Nick las saca de ahí: config, motor de reglas, o policy-as-code con OPA.

El contexto

ya no se concatena. Se arma.

Retriever, tools, estado, políticas. Dejó de ser un string y pasó a ser un componente con responsabilidad propia.

Dónde vive el conocimiento

pgvector
Qdrant
Cohere
Rerank
pgvector si ya tenés Postgres — no sumás infraestructura. Qdrant si querés open source dedicado; Pinecone o Weaviate hacen lo mismo, elegís por operación, no por capacidad. Y el reranker no es opcional: en 2026, BM25 más vectores más reranking es lo mínimo para que el retrieval sirva.

Cómo llega el resto

MCP
Postgres
OPA
Uno por función: MCP para llegar a las tools, Postgres para el estado, OPA para las políticas. MCP dejó de ser de Anthropic: en diciembre de 2025 se donó a la Agentic AI Foundation, con OpenAI y Google adentro. 28% de Fortune 500 en marzo 2026. Hoy es el estándar de integración, no una apuesta. Para políticas, Cedar es la alternativa — entró en Bedrock AgentCore.

05

La Evidencia

Sale mal y nadie sabe por qué

  • Qué documentos le llegaron
  • Qué devolvieron las tools
  • Con qué contexto terminó decidiendo
Acá entra tracing. LangSmith, OpenTelemetry, Phoenix. Un trace por ticket: latencia, tokens, costo, ejecución de cada nodo.

Respondió 200.

Y asignó mal el ticket.

Ejecutó bien

Que haya ejecutado bien no significa que haya decidido bien. Y eso ningún trace te lo dice.

Medirlo

  • Los tickets que ya se resolvieron
  • La respuesta correcta ya se conoce
  • Correr el sistema y contar cuántas acierta
Evals. Ground truth de equipo y prioridad. pytest más un harness, o LangSmith / OpenAI Evals. Precision, recall, matriz de confusión.

Antes: que el código no se rompa.

Ahora: que las decisiones no empeoren.

Cambia el prompt, cambia el modelo, cambia el retriever: se corre el dataset otra vez y se compara contra el baseline.

Queda registro

  • Qué evidencia se usó
  • Qué políticas aplicaron
  • Qué modelo decidió, y qué decidió
Traza de decisión persistida. Postgres más los traces de OTel o LangSmith.

Con qué se mide

OpenTelemetry
Langfuse
Ragas
OpenTelemetry para las trazas, Langfuse para verlas, Ragas para medir. LangSmith y Phoenix hacen lo mismo que Langfuse; DeepEval y Promptfoo, lo mismo que Ragas. Ojo con OpenTelemetry: las convenciones de GenAI todavía NO son estables. Siguen en development, pre-1.0, y en junio de 2026 las movieron a su propio repo sin release. Vale construir encima, pero se sigue moviendo.
